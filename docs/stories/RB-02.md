# RB-02 — Establish durable schema and migrations

Part of [Sprint 1 — Runnable foundation](../SPRINT_PLAN.md#4-detailed-stories). This story inherits the shared [definition of ready and done](../SPRINT_PLAN.md#5-shared-definition-of-ready-and-done).

**Status:** Done

**Sprint:** Sprint 1 — Runnable foundation

**Priority / Size / Owner:** P0 · M · backend/database

**Depends on:** [RB-01.md](RB-01.md)

## User story

As a developer, I can apply versioned schema changes so application state is durable and valid.

## Scope

Add numbered migrations under `db/migrations/` and a shell migration entry point. Create `documents`, `doc_chunks`, and the index-revision relationship first; subsequent owning stories add the remaining tables from [DATA_MODEL.md](../DATA_MODEL.md). Enable vector and required UUID support; define foreign keys, uniqueness, status constraints, and retrieval indexes appropriate to the selected dimensions.

## Tasks

- [x] Add numbered migrations under `db/migrations/` and a shell migration entry point
- [x] Create `documents`, `doc_chunks`, and the index-revision relationship in the first migrations
- [x] Enable vector and required UUID support
- [x] Define foreign keys, uniqueness, status constraints, and retrieval indexes appropriate to the selected dimensions
- [x] Make the migration runner idempotent — rerunning does not reapply completed migrations
- [x] Make migration failure visible, prevent ready status on failure, and ensure application startup does not silently create an alternative schema

## Acceptance criteria

- [x] A fresh database migrates successfully; rerunning the migration runner does not reapply completed migrations.
- [x] Invalid document/chunk relationships are rejected. Index revisions identify chunk settings and embedding compatibility.
- [x] Migration failure is visible and prevents ready status; application startup does not silently create an alternative schema.

## Verification

Apply migrations twice to a disposable database; exercise valid/invalid inserts and a failed migration in an isolated fixture; confirm stored records survive service restart.

Verification checklist (completed during implementation, exercised 2026-09-14 against a disposable `pgvector/pgvector:pg16` container via `sh scripts/migrate.sh --container …`; no external prerequisites beyond Docker):

- [x] Migrations applied twice to a disposable database without reapplication — second run reported "database schema is up to date; nothing to apply"; `status` listed versions 1–3 applied. A tampered tracking table (version recorded but tables dropped) fails loudly instead of guessing.
- [x] Valid and invalid inserts exercised in an isolated fixture — valid document → revision → chunk chain stored; rejected as expected: bad `documents.status`, duplicate `documents.checksum`, chunk whose `document_id` differs from its revision's document (composite FK), duplicate `(index_revision_id, chunk_index)`, negative `chunk_index`, `ready` revision without `published_at`, `failed` revision without `error_code`, wrong embedding dimension (`expected 1536 dimensions, not 3`), empty `content`.
- [x] Failed migration exercised in an isolated fixture — a deliberately broken `0004` failed with a syntax error, exited 1, named the failing file, rolled back completely (`broken_table` absent), and wrote no `schema_migrations` record. Checksum drift on an applied migration produces a visible warning without touching recorded state.
- [x] Stored records survive service restart — `docker restart` of the fixture kept documents and `schema_migrations` intact; the runner remained idempotent afterwards.

Additional implementation checks: `backend/internal/schema` unit tests cover the readiness rule (missing table, behind/above required version → structured errors); `schema.Check` was verified against the live fixture (unmigrated → error, migrated → nil); `go test ./...`, `go vet ./...`, and `go build ./...` pass. The API reports a `schema` check on `/readyz` (documented in `docs/API.md`); startup logs schema state but never creates or alters schema — migrations are applied out of band with `scripts/migrate.sh` (documented in `README.md` and `db/migrations/README.md`; schema contract in `docs/DATA_MODEL.md`).
