# RB-33 — Manage provider and model profiles in Settings

Part of Sprint 8 — Settings-managed RAG workspace. This story inherits the
shared definition of ready and done in `docs/SPRINT_PLAN.md`.

**Status:** Implemented; automated API/domain verification passes; migrated
database runtime verification remains open

**Sprint:** Sprint 8 — Settings-managed RAG workspace

**Priority / Size / Owner:** P0 · M · backend + platform

## User story

As a lab operator, I can register the model IDs I use under an existing
provider adapter without editing Go code or putting credentials in the UI.

## Tasks

- [x] Add the PostgreSQL `model_profiles` catalog and seed the shipped profiles
- [x] Expose `GET /api/v1/settings` for providers, profiles, prompts, rerankers,
  and UI limits
- [x] Expose `POST /api/v1/settings/model-profiles` with strict field and
  provider-kind validation
- [x] Keep API keys, endpoint secrets, and environment contents out of the
  request/response contract
- [x] Resolve Settings profiles into the existing Go provider interfaces
- [x] Allow Airflow embedding jobs to use a persisted model ID while retaining
  an explicit supported-provider boundary
- [x] Add API and model-profile behavioral tests

## Acceptance criteria

- [x] A new generation or embedding model identity can be persisted through the
  Settings API.
- [x] Unsupported provider/kind combinations, malformed names, missing model
  IDs, and invalid embedding dimensions fail visibly.
- [x] Existing RAG configurations retain concrete model/embedding identity even
  when a catalog entry changes later.
- [x] No credential value is accepted or returned by the Settings API.

## Verification

Run the model-profile and HTTP API unit tests, then apply migration `0021` to a
disposable PostgreSQL database and verify a Settings-created profile can be
selected by a new RAG configuration.
