# RB-29 — Validate financial document data deterministically

Part of Sprint 7 — Document intelligence assessment. This story inherits the shared definition of ready and done in `docs/SPRINT_PLAN.md`.

**Status:** Implemented; deterministic/unit verification passes

**Sprint:** Sprint 7 — Document intelligence assessment

**Priority / Size / Owner:** P0 · S/M · backend

**Depends on:** RB-28

## User story

As an assessment reviewer, I can see deterministic validation findings separately from the LLM extraction so arithmetic and business-rule inconsistencies are not hidden by fluent model output.

## Scope

Implement a versioned validation tool over normalized financial data. Validation remains deterministic and testable; the LLM does not decide whether its own arithmetic is correct.

## Tasks

- [x] Define validation finding severity/status and stable rule identifiers
- [x] Check required/important fields according to document type
- [x] Validate supported currency/date/amount representations
- [x] Validate date ordering when both relevant dates exist
- [x] Recalculate line-item extensions where quantity/unit price are available
- [x] Reconcile line-item/subtotal/tax/total relationships using an explicit decimal tolerance policy
- [x] Persist findings and validation-policy version
- [x] Add focused boundary tests for decimals, tolerance, missing values, and inconsistent totals
- [x] Document validation policy and known ambiguities in `ENGINEERING_NOTES.md`

## Acceptance criteria

- [x] Validation returns explicit pass/warning/failure findings with stable rule identifiers.
- [x] Financial arithmetic uses deterministic decimal logic, not LLM judgment.
- [x] Missing fields and inconsistent totals are surfaced to the final result.
- [x] Validation policy/version is traceable and boundary-tested.

## Verification

Run a clean valid fixture plus intentionally inconsistent/missing-field fixtures and record exact findings in `docs/SPRINT_7_VERIFICATION.md`.
