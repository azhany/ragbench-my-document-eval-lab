# RB-02 — Establish durable schema and migrations

Part of [Sprint 1 — Runnable foundation](../SPRINT_PLAN.md#4-detailed-stories). This story inherits the shared [definition of ready and done](../SPRINT_PLAN.md#5-shared-definition-of-ready-and-done).

**Status:** Not started

**Sprint:** Sprint 1 — Runnable foundation

**Priority / Size / Owner:** P0 · M · backend/database

**Depends on:** [RB-01.md](RB-01.md)

## User story

As a developer, I can apply versioned schema changes so application state is durable and valid.

## Scope

Add numbered migrations under `db/migrations/` and a shell migration entry point. Create `documents`, `doc_chunks`, and the index-revision relationship first; subsequent owning stories add the remaining tables from [DATA_MODEL.md](../DATA_MODEL.md). Enable vector and required UUID support; define foreign keys, uniqueness, status constraints, and retrieval indexes appropriate to the selected dimensions.

## Tasks

- [ ] Add numbered migrations under `db/migrations/` and a shell migration entry point
- [ ] Create `documents`, `doc_chunks`, and the index-revision relationship in the first migrations
- [ ] Enable vector and required UUID support
- [ ] Define foreign keys, uniqueness, status constraints, and retrieval indexes appropriate to the selected dimensions
- [ ] Make the migration runner idempotent — rerunning does not reapply completed migrations
- [ ] Make migration failure visible, prevent ready status on failure, and ensure application startup does not silently create an alternative schema

## Acceptance criteria

- [ ] A fresh database migrates successfully; rerunning the migration runner does not reapply completed migrations.
- [ ] Invalid document/chunk relationships are rejected. Index revisions identify chunk settings and embedding compatibility.
- [ ] Migration failure is visible and prevents ready status; application startup does not silently create an alternative schema.

## Verification

Apply migrations twice to a disposable database; exercise valid/invalid inserts and a failed migration in an isolated fixture; confirm stored records survive service restart.

Verification checklist (to be completed during implementation):

- [ ] Migrations applied twice to a disposable database without reapplication
- [ ] Valid and invalid inserts exercised in an isolated fixture
- [ ] Failed migration exercised in an isolated fixture
- [ ] Stored records survive service restart
