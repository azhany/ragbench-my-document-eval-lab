## User story

As a user, I can open the application and see whether its backend is reachable before beginning a workflow.

## Scope

Create Vue navigation for Overview, Library, Chat, Evaluations, Experiments, Monitor; use one API client and a working config list. Unimplemented destinations remain explicitly unavailable until their stories land, without fake metrics or sample success states.

## Tasks

- [x] Create Vue navigation for Overview, Library, Chat, Evaluations, Experiments, Monitor
- [x] Implement one API client shared by the shell
- [x] Implement a working config list backed by the running backend
- [x] Keep unimplemented destinations explicitly unavailable — no fake metrics or sample success states
- [x] Implement distinct loading, empty, and unavailable states
- [x] Show an actionable error on backend failure instead of a blank page; keep model secrets out of browser configuration
- [x] Keep state component-local except for proven shared needs

## Acceptance criteria

- [x] Navigation and config data use the running backend; loading, empty, and unavailable states are distinct.
- [x] A backend failure gives an actionable error instead of a blank page. No model secrets reach browser configuration.
- [x] State remains component-local except for proven shared needs.

## Verification

Browser-drive navigation, retrieve a persisted configuration, and stop the API to observe the visible failure state.

Verification checklist (completed 2026-09-14 against the running Compose stack with the rebuilt backend and frontend images; navigation driven with headless Google Chrome (`--headless=new --dump-dom`) against `http://localhost:5173`, plus 12 vitest component/client/router tests):

- [x] Navigation browser-driven across all six destinations — headless Chrome rendered every route (`/`, `/library`, `/chat`, `/evaluations`, `/experiments`, `/monitor`): all six nav entries present, Overview shows stack status + config list, unimplemented destinations show the explicit "Not available yet" state naming their owning stories (e.g. Chat → RB-09–RB-12) with no sample data.
- [x] A persisted configuration retrieved and displayed — `ui-smoke-config` was created through `POST /api/v1/rag-configs` via the nginx proxy (the exact browser path, HTTP 201) and rendered by the browser in the Overview config list with model profile, embedding identity, and no secrets.
- [x] API stopped and the visible failure state observed — `docker compose stop backend`, then headless Chrome on `/` showed the error state (`data-state="error"` on the config list, `data-state="unreachable"` on health cards, "Could not load configurations", the actionable `docker compose ps backend` hint, and a Retry button) instead of a blank page. After `docker compose start backend` the list recovered and displayed the persisted config.

Additional implementation checks: `npm test` (12 tests) covers client error normalization (unreachable, structured envelope, non-JSON 502, JSON content type), ConfigList loading/ready/empty/error/unavailable-capability rendering, and all six router destinations; `npm run build` and the frontend Docker build succeed with the new `vue-router`/`vitest` dependencies. Backend API stopped/restarted during this verification also re-confirmed RB-03 persistence across restart.
