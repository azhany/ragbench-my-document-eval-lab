# RB-14 — Orchestrate durable evaluation runs

Part of [Sprint 4 — Repeatable evaluation](../SPRINT_PLAN.md#4-detailed-stories). This story inherits the shared [definition of ready and done](../SPRINT_PLAN.md#5-shared-definition-of-ready-and-done).

**Status:** Implemented (RB-14). Durable eval runs pin dataset version, config identity, corpus revisions and evaluator policy; case execution runs the same Go pipeline with `request_type=evaluation`; results are idempotent per (run, case); aggregate status distinguishes completed/partial/failed; dispatch failures persist as `dispatch_failed` with a reason; the `rag_evaluation` DAG drives the Go API only. Live run `21c6c709-8781-42a9-b009-f812ba5703d9` pinned the 20-case golden version and all four corpus revision identities; all 20 cases reached terminal `model_rate_limited` failures from opencode-go HTTP 429, so no quality values were fabricated.

**Sprint:** Sprint 4 — Repeatable evaluation

**Priority / Size / Owner:** P0 · L · backend/pipeline

**Depends on:** [RB-13 — Maintain a versioned golden dataset](RB-13.md)

## User story

As an evaluator, I can launch a dataset against a named config so every case uses the normal Go query pipeline.

## Scope

Migrate `eval_runs`/`eval_results`; implement create/list/detail/results APIs and `rag_evaluation` DAG. Go exposes the same query path with evaluation request attribution; Airflow calls it per case and records run/result/trace relationships.

## Tasks

- [x] Add numbered migrations for `eval_runs` and `eval_results` under `db/migrations/`, pinning dataset, config, corpus/index revision, and evaluator policy per run
- [x] Implement evaluation run create/list/detail/results APIs in Go
- [x] Expose the normal Go query path with evaluation request attribution so evaluation cases run through the same pipeline as chat
- [x] Implement `rag_evaluation` DAG dispatch: call the Go API per case and record run/result/trace relationships
- [x] Make case/task retries idempotent so completed results are not duplicated
- [x] Track per-case status and aggregate run status that distinguish completed, partial, and failed work
- [x] Surface Airflow dispatch failure as a visible run failure, never as successful processing

## Acceptance criteria

- [ ] Run creation pins dataset, config, corpus/index revision, and evaluator policy; every attempted case has status and a query trace or explicit pre-query failure.
- [ ] Retries do not duplicate completed results. A case/provider failure remains visible; run status and aggregation distinguish completed, partial, and failed work.
- [ ] Airflow dispatch failure is surfaced; Python does not duplicate retrieval, prompt construction, or generation logic.

## Verification

Small dataset DAG smoke run through real Go API; one injected failed case and one retried task; verify run status, unique results, trace links, and immutable inputs in PostgreSQL.

Live evidence: run `86187c9f-4142-48d9-aabd-79d60ef32c3f` completed one HF/opencode case with a judge trace; run `21c6c709-8781-42a9-b009-f812ba5703d9` finalized `failed` with 20 visible `model_rate_limited` result rows and pinned inputs.
