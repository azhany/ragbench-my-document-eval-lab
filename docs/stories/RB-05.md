## User story

As a developer/evaluator, I can upload a document and receive its queued identity so processing can begin asynchronously.

## Scope

Implement `POST /api/v1/documents`, list/detail routes, durable metadata and shared-volume storage; validate allowed files and configured size bounds; associate ingestion config and trigger `document_ingestion` in Airflow. Persist dispatch correlation and errors.

## Tasks

- [x] Implement `POST /api/v1/documents` plus list/detail routes
- [x] Store durable document metadata and uploaded bytes on the shared volume
- [x] Validate allowed file formats and the configured size bound
- [x] Associate the ingestion config and trigger `document_ingestion` in Airflow via its supported API
- [x] Persist dispatch correlation IDs, job/run state, and dispatch errors
- [x] Return the persisted document with queued status for accepted uploads; keep the batch pipeline out of the synchronous request path
- [x] Return documented errors for unsupported/oversized uploads and storage/dispatch failures; ensure partial uploads do not appear processed or leave unexplained records/files
- [x] Prevent file names escaping the upload directory and duplicate/retried dispatch creating duplicate active ingestion for the same document revision

## Acceptance criteria

- [x] Accepted PDF/DOCX/TXT uploads return the persisted document with queued status; Go does not perform the batch pipeline synchronously.
- [x] Unsupported/oversized uploads and storage/dispatch failures return documented errors; partial uploads do not appear processed or leave unexplained records/files.
- [x] File names cannot escape the upload directory. Duplicate/retried dispatch cannot create duplicate active ingestion for the same document revision.

## Verification

HTTP multipart upload → queued database row and Airflow run; rejected format/size/path-name cases; unavailable Airflow produces a visible dispatch failure and a documented recovery path.

Verification checklist (to be completed during implementation):

- [x] HTTP multipart upload produces a queued database row and an Airflow run
- [x] Rejected format, size, and path-name cases return documented errors
- [x] Unavailable Airflow produces a visible dispatch failure and a documented recovery path

Dispatch outages/conflicts use controlled HTTP failures and persisted-store tests;
the normal dispatch path also ran against the actual Airflow 3.0.6 API. Recovery
uses the added `retry-dispatch` route and read-only source reconciliation script.
